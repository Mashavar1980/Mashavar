# Объяснение кода и контрольные вопросы — вариант 3

## Назначение

Конвертер принимает сумму и два кода валют, проверяет ввод, пересчитывает сумму и сохраняет запись в памяти. Курсы фиксированные, учебные. Например: 90 RUB / 90 × 0.92 = 0.92 EUR. Общая формула: сумма / курс исходной валюты × курс целевой валюты. Курсы выражают количество валюты за 1 USD.

Используется JavaScript Number с округлением до двух знаков. Это учебная модель, а не банковский учет с индивидуальными правилами округления для каждой валюты. История очищается после завершения процесса, что допустимо для этого задания.

## Объяснение по блокам

1. **exchangeRates.js.** Object.freeze запрещает изменение таблицы во время исполнения. API не используется, поэтому результат не зависит от интернета и времени проверки.
2. **validation.js.** normalizeCurrency убирает пробелы и переводит код в верхний регистр. Object.hasOwn проверяет именно собственное свойство, отклоняя constructor и __proto__. validateAmount допускает только конечное неотрицательное число. Библиотечный API отклоняет строку '100', а CLI явно преобразует аргумент через Number.
3. **currencyConverter.js.** constructor создает отдельную history. convert сначала проверяет ввод и результат, а после успешного пересчета записывает сумму, коды, результат и ISO-дату. Ошибочные операции не сохраняются. getHistory возвращает копии объектов, чтобы вызывающий код не испортил исходные записи. clearHistory очищает массив. Дополнительный getLastConversion добавляется при выполнении раздела 8 инструкции.
4. **app.js.** main получает аргументы; без аргументов запускает демонстрацию. require.main === module отличает прямой запуск от импорта. Ошибки выводятся в stderr, код завершения становится 1. Успешная консольная программа завершает работу с кодом 0.
5. **Тесты.** Jest сравнивает результат с ожидаемым. beforeEach создает чистый конвертер. test.each проверяет несколько входов. toThrow проверяет ошибки. Интеграционные тесты запускают Node через process.execPath и проверяют stdout и exit code; тайм-аут защищает от зависания.
6. **Сборка.** build.js очищает dist и копирует туда src. Команды Linux не нужны, поэтому сборка работает в Windows. Транспиляция простого JavaScript не требуется.
7. **Docker.** Development устанавливает зависимости. Test выполняет lint, тесты и build. Production копирует только dist, запускается от пользователя node, не содержит Jest/ESLint. Приложению не нужен открытый сетевой порт.
8. **CI/CD.** needs задает порядок и останавливает зависимые jobs при ошибке. Матрица проверяет Node 22/24. Cache npm ускоряет скачивание, но не заменяет npm ci. Docker проверяется до публикации. Buildx публикует amd64/arm64; QEMU обеспечивает сборочные команды другой архитектуры. Runtime smoke test выполняется на архитектуре runner. Deploy — учебный echo, а не настоящий удаленный сервер.

## Что исправлено относительно примеров методички

- Объявлена именованная стадия AS development.
- Консольный контейнер проверяется docker run; ожидание сервера и docker exec после завершения не используются.
- Тесты выполняются в test-стадии, а не в production без тестовых зависимостей.
- Выбирается реальный файл converter.test.js вместо несовпадающего шаблона currency.
- lint запускает ESLint, а не просто печатает сообщение об успехе.
- Сборка работает в Windows; инструкции используют PowerShell и VS Code вместо sed/cat/cp.
- npm ci использует package-lock.json; кеш включен явно.
- Основной ci.yml объединяет базовый и расширенный pipeline. Дублирующий advanced-ci.yml не требуется.
- Node 16/18/20 заменены на 22/24.
- MOCK_API оставлен в валютном workflow для соответствия примеру, но не переключает режимы: фиксированные курсы используются всегда.

## Ответы на контрольные вопросы

### 1. Merge и rebase

Merge объединяет истории, сохраняя исходные коммиты; --no-ff создает отдельный merge-коммит. Rebase повторно применяет коммиты поверх новой базы, меняя их SHA. Merge удобен для интеграции общей работы, rebase — для обновления собственной еще не опубликованной ветки. Не переписывайте чужую опубликованную историю без согласования.

### 2. Cherry-pick

Переносит изменения выбранного коммита в текущую ветку, создавая новый коммит. Полезен для отдельного исправления без переноса остальных функций ветки. Здесь переносится Document test command. Если возникает конфликт, после его разрешения нужны git add и git cherry-pick --continue.

### 3. Stash

Временно сохраняет незакоммиченные изменения и освобождает рабочую папку. list показывает записи, apply применяет без удаления, pop применяет и удаляет после успеха. Для новых неотслеживаемых файлов нужен -u. В обоих упражнениях меняются уже отслеживаемые файлы.

### 4. Преимущества CI/CD

CI выявляет ошибки при изменении кода, CD автоматизирует подготовку и доставку проверенного результата. Повышаются воспроизводимость и скорость обратной связи. Здесь доставка действительно публикует контейнер в GHCR, а развертывание показано только учебными echo-шагами.

### 5. Структура workflow

YAML в .github/workflows: name — имя; on — события; permissions — права токена; jobs — задачи; runs-on — runner; steps — последовательность шагов. uses подключает action, run выполняет команду, needs задает зависимости, if — условия, strategy.matrix — набор конфигураций, environment — среду и ее правила одобрения.

### 6. Безопасность

Не хранить токены в исходниках; использовать GITHUB_TOKEN/Secrets, минимальные права, аудит зависимостей, review и защиту веток. Не публиковать из непроверенных PR. Защищать production одобрением среды. В производственных проектах сторонние actions закрепляют полными SHA; здесь используются читаемые major-теги, как в методичке, что не гарантирует неизменности внешнего кода.

### 7. Matrix build

Один job запускается несколько раз с разными параметрами. Здесь Node 22 и 24 проверяются отдельно и параллельно. Это выявляет несовместимости, невидимые на единственной версии.

### 8. Docker в CI/CD

Dockerfile описывает окружение приложения. CI собирает образ, проверяет его и отправляет в реестр; среда затем может запустить тот же образ. Многостадийная сборка отделяет тестовые инструменты от конечного приложения. Контейнеры используют ядро хоста и не являются полноценными виртуальными машинами.

## Зависимости и аудит

Вместо Jest 29 из методички используется Jest 30; настройки и тесты адаптированы и проверены. ESLint 10 требует Node 22.13+ либо 24+. В package.json задан узкий override для @istanbuljs/load-nyc-config → js-yaml 4. Он исключает старую цепочку js-yaml 3 → argparse 1 → sprintf-js, отмеченную аудитом. Загрузчик использует совместимый метод js-yaml.load; в проекте нет пользовательских NYC YAML-конфигураций. После замены повторно проверены чистая установка npm ci, тесты и coverage. Override не отключает аудит; при последующих обновлениях его следует пересмотреть.
